## IMO Solver Project (`/solver`)

### Overview
A sophisticated multi-agent LLM system for solving IMO-level mathematical problems using 5 specialized agents in a hierarchical pipeline.

### Common Development Commands

```bash
# Run the main solver pipeline
cd solver
python -m solver.main

# Run specific test scripts
python test_parallel_trajectories_clean.py  # Test parallel trajectory mode
python test_thinking_streaming.py          # Test streaming functionality

# Run tests with pytest (if installed)
python -m pytest
```

### Architecture

**5-Agent Pipeline** (defined in `pipeline.py`):
1. **Generator Agent** - Creates initial solution attempts
2. **Self-Improvement Agent** - Refines incomplete solutions
3. **Verifier Agent** - Identifies errors in solutions
4. **Meta-Verifier Agent** - Reviews and filters bug reports
5. **Correction Agent** - Produces corrected final solutions

**Key Files**:
- `main.py` - Main entry point with checkpoint/resume support
- `main_parallel_trajectories.py` - Parallel trajectory mode implementation
- `pipeline.py` - Core agent workflow and LLM integration
- `prompts.py` - Agent persona templates (based on Huang & Yang 2025)
- `config.yaml` - Central configuration for LLM and pipeline parameters
- `utils.py` - Helper functions for file operations

### Configuration (`config.yaml`)

```yaml
# Key settings:
problem_id: 'asml'                    # Problem to solve
model_name: 'gemini-2.5-pro'          # LLM model
temperature: 0.1                      # For consistent reasoning
max_correction_loops: 125             # Max verification iterations
final_verification_passes: 4          # Final check passes
enable_parallelization: true          # Parallel processing
parallel_trajectory_mode: true        # Multiple solution paths
```

### Pipeline Features

- **Checkpoint/Resume**: Automatic checkpoint saving after each stage
- **Parallel Processing**: Initial generation and final verification can run in parallel
- **Parallel Trajectories**: Each initial sample runs through entire pipeline independently
- **Streaming Support**: OpenAI endpoint supports streaming to prevent timeouts
- **XML-Structured Output**: Solutions use `<answer>`, `<solution>`, `<reflection>` tags
- **LaTeX Support**: Mathematical notation within $ delimiters

### Adding New Problems

1. Create `.md` file in `solver/problems/` with LaTeX math
2. Update `problem_id` in `config.yaml`
3. Run: `cd solver && python -m solver.main`
4. Outputs saved to `solver/outputs/{problem_id}/`

The `call_llm()` function in `pipeline.py` requires implementation with actual API calls (supports both Gemini and OpenAI endpoints).

## Agent Development Kit (ADK) Documentation (`/adk-docs`)

### Overview
Contains comprehensive documentation and examples for Google's Agent Development Kit - an open-source, code-first toolkit for building, evaluating, and deploying AI agents. While optimized for Gemini and Google ecosystem, ADK is model-agnostic and deployment-agnostic.

### Key Features
- **Rich Tool Ecosystem**: Pre-built tools, custom functions, OpenAPI specs integration
- **Code-First Development**: Define agent logic in Python and Java
- **Modular Multi-Agent Systems**: Compose specialized agents into hierarchies
- **Built-in Observability**: Tracing and monitoring with AgentOps support
- **Deploy Anywhere**: Cloud Run or Vertex AI Agent Engine deployment

## Project Overview

Gemini Balance is a FastAPI-based proxy and load balancer for the Google Gemini API. It provides:
- Multiple API key management with automatic rotation and load balancing
- OpenAI API format compatibility alongside native Gemini API format
- Visual configuration interface with real-time updates
- Comprehensive monitoring and error logging
- Support for image generation, web search, and text-to-speech models

## Development Commands

### Running the Application

```bash
# Local development with hot reload
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload

# Docker Compose (production)
docker-compose up -d

# Docker run (production)
docker run -d -p 8000:8000 --name gemini-balance \
  -v ./data:/app/data \
  --env-file .env \
  ghcr.io/snailyp/gemini-balance:latest
```

### Development Setup

```bash
# Install dependencies
pip install -r requirements.txt

# Create virtual environment (optional)
python -m venv myenv
source myenv/bin/activate  # Linux/Mac
# or
myenv\Scripts\activate  # Windows
```

## Architecture Overview

### Core Application Structure

The application follows a layered architecture with clear separation of concerns:

1. **Entry Point**: `app/main.py` - Loads environment variables and creates the FastAPI app
2. **Application Factory**: `app/core/application.py` - Manages app lifecycle, database connections, and scheduler
3. **Configuration**: `app/config/config.py` - Centralized settings management using Pydantic
4. **Database Layer**: `app/database/` - SQLAlchemy models and database services
5. **Service Layer**: `app/service/` - Business logic for chat, keys, stats, etc.
6. **Router Layer**: `app/router/` - API endpoints organized by functionality
7. **Middleware**: `app/middleware/` - Request processing and smart routing

### Key Components

#### API Key Management (`app/service/key/key_manager.py`)
- Manages multiple Gemini API keys with automatic rotation
- Tracks key failures and automatically disables problematic keys
- Supports re-checking disabled keys at configurable intervals

#### Chat Services
- **Gemini**: `app/service/chat/gemini_chat_service.py` - Native Gemini API handling
- **OpenAI**: `app/service/chat/openai_chat_service.py` - OpenAI format compatibility
- **Vertex Express**: `app/service/chat/vertex_express_chat_service.py` - Vertex AI support

#### Model-Specific Features
- **Image Models**: Configured via `IMAGE_MODELS`, accessed with `{model}-image` suffix
- **Search Models**: Configured via `SEARCH_MODELS`, accessed with `{model}-search` suffix
- **Thinking Models**: Support for models with thinking/reasoning capabilities

#### Configuration Management
- Visual configuration interface at `/config-editor` (requires auth)
- Real-time configuration updates without restart
- Database-backed configuration persistence

## API Endpoints

### Gemini Format
- Base URL: `http://localhost:8000/gemini/v1beta`
- `GET /models` - List available models
- `POST /models/{model_name}:generateContent` - Generate content
- `POST /models/{model_name}:streamGenerateContent` - Stream content

### OpenAI Format
- Base URL: `http://localhost:8000/openai/v1` or `/hf/v1`
- `GET /models` - List models
- `POST /chat/completions` - Chat completion
- `POST /embeddings` - Text embeddings
- `POST /images/generations` - Image generation

### Admin Endpoints (Require AUTH_TOKEN)
- `/keys_status` - Monitor API key status
- `/error-logs` - View error logs
- `/config-editor` - Edit configuration

## Configuration

Key environment variables (set in `.env`):
- `API_KEYS` - List of Gemini API keys (required)
- `ALLOWED_TOKENS` - Access tokens for API authentication (required)
- `AUTH_TOKEN` - Admin token for configuration access
- `DATABASE_TYPE` - `mysql` or `sqlite`
- `TEST_MODEL` - Model for testing key validity (default: `gemini-1.5-flash`)

## Testing Approach

Since this project doesn't have a formal test suite, testing should be done manually:

```bash

curl -X POST http://localhost:8000/gemini/v1beta/models/gemini-1.5-flash:generateContent \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"contents":[{"parts":[{"text":"Hello"}]}]}'

  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
```

## Database

The application supports both SQLite and MySQL:
- SQLite: Default for development, database file at `data/gemini_balance.db`
- MySQL: Recommended for production, configured via docker-compose

Database models are defined in `app/database/models.py` and include:
- `Keys` - API key management
- `Configs` - Dynamic configuration storage
- `RequestLogs` - Request tracking
- `ErrorLogs` - Error tracking

## Monitoring and Debugging

1. **Logs**: Application logs are written to console and can be configured via `LOG_LEVEL`
2. **Error Logs**: Accessible via `/error-logs` endpoint with detailed error information
3. **Key Status**: Monitor API key health at `/keys_status`
4. **Request Logs**: Track all API requests (configurable retention)

## Scheduled Tasks

The application uses APScheduler for background tasks (`app/scheduler/scheduled_tasks.py`):
- Periodic key status checks
- Automatic log cleanup
- Re-checking disabled keys

## Important Notes

- When testing with `gemini-2.5-pro` as mentioned in the existing CLAUDE.md
- The application supports multiple database backends (MySQL/SQLite)
- Configuration changes through the UI take effect immediately
- Failed API keys are automatically rotated and can be re-enabled after the check interval
